NOTE: **Level Set -- What is the EVPN VXLAN Underlay and Why It Must Be Solid Before the Overlay** +
The **underlay** is the routed Layer 3 network that carries all traffic between spines and leafs in an EVPN VXLAN fabric. It has one job: give every leaf a reachable path to every other leaf's loopback address so that VXLAN tunnels can form between them. Without a working underlay, the overlay has no transport -- VTEP-to-VTEP tunnels cannot establish, BGP EVPN peering sessions will not come up, and no tenant traffic crosses the fabric. +
 +
**How the underlay works** +
Each spine-leaf link uses a point-to-point /31 subnet configured in the base module. On top of these links, an Interior Gateway Protocol -- in this lab, **OSPF** -- advertises all loopback and point-to-point prefixes so that every switch has a route to every other switch's Loopback0. These loopback addresses are critical: they serve as the **router ID** for BGP, the **VTEP source** for VXLAN tunnels, and the **BGP peering address** for the EVPN overlay. Once OSPF has converged, **iBGP** sessions are established between each leaf and both spines using the loopback addresses as peering endpoints. At this stage BGP carries only the underlay address families -- the EVPN address family is added later in the overlay module. OSPF provides reachability; BGP provides the peering mesh that the overlay will extend. +
 +
**Why automate and test the underlay before deploying the overlay?** +
The overlay is entirely dependent on the underlay for transport. If an OSPF adjacency is missing between a spine and a leaf, that leaf's loopback will be unreachable from other leafs -- which means VXLAN tunnels to that VTEP will never establish and BGP EVPN sessions will fail to connect. These failures are silent at the overlay layer: EVPN simply never converges, with no clear indication that the root cause is a missing OSPF route two layers below. By automating the underlay deployment with Ansible and running connectivity tests -- verifying OSPF neighbor adjacencies, confirming that all loopbacks are reachable from every leaf, and checking that BGP peering sessions reach the Established state -- you prove the transport layer works before adding the complexity of VXLAN and EVPN on top of it. Catching a wrong OSPF area ID, a missing network statement, or an incorrect BGP neighbor address at this stage takes minutes to fix and re-deploy. Discovering the same error after the overlay is deployed means troubleshooting across OSPF, BGP, VXLAN, and EVPN simultaneously -- a process that can take hours and affects the entire fabric.

The underlay section takes a *hybrid approach* to configuring the multi-vendor VXLAN EVPN fabric, using Ansible resource modules where they work well and falling back to Jinja2 templates where they don't.

== Resource Modules for the Simple, Structured Stuff

For base fabric and underlay features with clean, declarative data models -- interfaces, IP addressing, VLANs, L2 switchports, hostnames -- we use vendor-specific resource modules like `arista.eos.eos_l3_interfaces` and `cisco.nxos.nxos_l3_interfaces`. The variable data in `host_vars` maps directly to the module schema, so the task files stay concise:

[source,yaml]
----
- name: Configure L3 IP Properties [Arista]
  arista.eos.eos_l3_interfaces:
    config: "{{ base_l3_interfaces }}"
    state: merged
----

Resource modules give us idempotency for free, built-in validation, structured error messages, and a consistent pattern across EOS and NX-OS. For compliance enforcement (NTP, logging, SNMP), we use the same modules with `state: replaced` to ensure devices match the declared config exactly.

== The Pattern by Deployment Stage

The split follows a natural complexity gradient:

Base config (section 1-4)::
Nearly 100% resource modules. Simple interface, IP, and VLAN configuration maps cleanly to module schemas.

Underlay (section 1-5)::
Hybrid. Resource modules handle interface properties and IP addressing. Templates handle OSPF process details and BGP peering.

The hybrid approach uses the best tool for each job -- resource modules where they are mature and reliable, templates where we need more control or have no other option.

=== The template rendered into CLI config

The `module_args.src` field shows the final rendered output of `eos_bgp.j2` -- the template took the structured `bgp_global` and `bgp_address_family` variables from `host_vars/spine1.yaml` and produced the exact EOS CLI syntax:

[source,cli]
----
router bgp 65000
   router-id 10.0.255.101
   no bgp default ipv4-unicast
   neighbor LEAF-PEERS peer group
   neighbor LEAF-PEERS remote-as 65001
   ...
----

=== What it configured on spine1

This sets up spine1 as a BGP EVPN route reflector/peer for the fabric:

* **AS 65000** with `router-id 10.0.255.101` (spine1's loopback)
* **`no bgp default ipv4-unicast`** -- disables IPv4 unicast by default since BGP here is only for EVPN overlay signaling, not underlay routing (OSPF handles that)
* **Peer group `LEAF-PEERS`** -- groups all four leaf neighbors under one configuration with `remote-as 65001`, sourced from Loopback0, eBGP multihop 3, and extended communities (needed for EVPN route targets)
* **Four neighbors** (`10.0.250.11` -- `.14`) -- the loopback IPs of leaf1 through leaf4, all using the `LEAF-PEERS` peer group
* **Address-family EVPN** -- activates the leaf peers for EVPN and sets `next-hop-unchanged` so spine1 does not rewrite the VTEP next-hop when reflecting EVPN routes between leaves

=== The diff and session

The `diff.prepared` shows EOS's config session diff -- everything is a `+` line because this BGP config did not exist on the device before. EOS uses a session-based config model (`ansible_178457393233-session-config`), so the module opens a config session, applies the changes, compares against running-config, and commits.

=== The warning

[quote]
____
To ensure idempotency and correct diff the input configuration lines should be similar to how they appear if present in the running configuration
____

This is a standard `eos_config` warning. It is telling you that if you run this playbook again, idempotency depends on the template output matching the device's running-config formatting exactly (indentation, ordering). This is one of the tradeoffs of using templates over resource modules -- resource modules handle idempotency comparison internally, but with `eos_config` + a template, you are responsible for matching the device's CLI formatting. In practice this usually works fine, but it is why `changed: true` might appear on a re-run if the device normalizes the config slightly differently than the template renders it.

== Relationship to the Underlay Deployment

The underlay deployment (`deploy_underlay.yml`) uses a hybrid of resource modules and Jinja2 templates to configure two protocol layers:

OSPF (underlay routing)::
Establishes point-to-point adjacencies over the physical spine-leaf links and advertises loopback addresses so every device can reach every other device's loopback. Configured using resource modules (`eos_ospf_interfaces`, `nxos_ospf_interfaces`) for per-interface settings and Jinja2 templates (`eos_ospf.j2`, `nxos_ospf.j2`) for the OSPF process itself.

BGP EVPN (overlay signaling)::
Establishes eBGP sessions between spine and leaf loopbacks (AS 65000 on spines, AS 65001 on leafs) to carry EVPN Type-2/3/5 routes for the overlay. Configured entirely via Jinja2 templates (`eos_bgp.j2`, `nxos_bgp.j2`) because the BGP resource modules had complex data type requirements. BGP EVPN depends on OSPF -- without loopback reachability, the eBGP multihop sessions cannot establish.

The test playbook validates that both layers are working and that the dependency chain holds: OSPF brings up loopback routes, loopbacks become reachable, and BGP sessions establish over those loopbacks.
