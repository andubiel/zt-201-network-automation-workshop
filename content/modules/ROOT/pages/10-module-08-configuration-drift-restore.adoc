= 1-8: Configuration Drift Restore
:source-highlighter: rouge
:toc: macro
:toclevels: 1

One of the key benefits of using Ansible Automation Platform is the ability to detect and remediate **configuration drift** -- the gradual divergence between a device's running configuration and its intended state. Drift happens constantly in production networks: an engineer makes a manual CLI change during a late-night outage, a firmware upgrade resets a default, or a misconfigured automation job overwrites a critical setting. Without a systematic way to detect these changes, drift accumulates silently until it causes an outage, a security exposure, or a compliance violation that is difficult to trace back to its origin.

In the Backups as Code module (1-2), you built the foundation for drift detection and recovery. The backup workflow captures each device's running configuration and commits it to a named Git branch in Gitea, creating a versioned, timestamped snapshot of the entire fabric's state. Every backup branch is a restore point -- if drift is detected or a configuration change goes wrong, the restore workflow can select any previous backup branch from a self-service survey and push that exact configuration back to the devices, returning them to a known-good state.

This module builds on that foundation. Where the backup module captured snapshots, this module uses those snapshots to **detect drift** by comparing the current running configuration against the last known-good backup, and to **restore** devices when drift is found. The combination of automated backups, drift detection, and one-click restores closes the loop: you can prove that your network matches its intended state at any point in time, and when it does not, you can fix it in minutes rather than hours of manual troubleshooting.

== Learning objectives

This section covers:

* Creating a known-good backup snapshot (`final_configs`) that captures the completed fabric state after all configuration modules have been applied
* Detecting configuration drift by comparing a device's running configuration against an intended state stored in a Git branch using `diff_against: intended`
* Reading diff output to identify exactly which lines have been added, removed, or changed on each device -- and understanding why `changed: true` does not mean the device was modified
* Deciding how to resolve drift: restoring devices to a previous backup branch or updating the intended config to accept the current state
* Restoring device configurations from named Git branches using the self-service restore workflow

== Overview

The `1-2-backups_as_code/intended.yml` playbook compares the live running configuration on each device against an intended (golden) configuration stored in a Git branch on Gitea. It does not push any changes to the devices -- it only reports what differs between the intended state in Git and the actual state on the wire.

This is a compliance-check pattern: the source of truth lives in version control, and the playbook tells you how far the network has drifted from it.

== How It Works

The playbook has two parts:

=== Part 1: Clone the Intended Config from Gitea

[source,yaml]
----
- name: Retrieve a repository from a distant location and make it available to the local EE
  ansible.scm.git_retrieve:
    origin:
      url: "http://gitea:{{ password }}@containerlab:8181/gitea/201-multi-vendor-vxlan-workshop.git"
    parent_directory: /tmp/
    branch:
      name: "{{ branch_name }}"
  delegate_to: localhost
  run_once: true
----

The `ansible.scm.git_retrieve` module clones the workshop repository from the Gitea server into `/tmp/` on the Ansible control node. The `branch_name` variable (passed as a survey prompt) selects which branch contains the intended configs. `run_once: true` ensures the clone only happens once (delegated to localhost via spine2), not once per device.

The intended config files live at: `/tmp/201-multi-vendor-vxlan-workshop/201_network_backup_files/<hostname>/<hostname>.cfg`

=== Part 2: Diff Against Running Config

The playbook uses `diff_against: intended` on the vendor-specific config modules:

* *NX-OS devices* -- `cisco.nxos.config` with `intended_config` loaded via `lookup('file', ...)`
* *EOS devices* -- `arista.eos.eos_config` with the same pattern

Each module pulls the running config from the device, compares it against the intended config from Git, and reports the diff. It does not apply any changes -- `diff_against: intended` is read-only.

== What the Diff Shows

Every device shows the same type of drift: the running config has an `snmp-server community vxlan` line that is *not* present in the intended config stored in Git.

=== EOS Devices (spine1, spine2, leaf1, leaf2)

[source,diff]
----
--- before
+++ after
@@ -3,7 +3,6 @@
 transceiver qsfp default-mode 4x10G
 service routing protocols model multi-agent
 hostname spine1
-snmp-server community vxlan ro
 spanning-tree mode mstp
----

The `-` prefix means this line exists in the running config (`before`) but not in the intended config (`after`). The SNMP community string `vxlan` with read-only access was added to the devices (by the `1-7-tuning_for_scale` SNMP playbook) but was never committed back to the intended config branch in Git.

=== NX-OS Devices (leaf3, leaf4)

[source,diff]
----
--- before
+++ after
@@ -37,7 +37,6 @@
 rmon event 5 log trap public description INFORMATION(5) owner PMON@INFO
-snmp-server community vxlan group network-operator
 fabric forwarding anycast-gateway-mac 0011.2233.4455
----

Same drift, different syntax. On NX-OS the SNMP community maps to the `network-operator` role group instead of EOS's `ro` keyword, but the meaning is the same -- the SNMP community was configured on the device but the intended config in Git doesn't include it.

----

spine2 shows `ok=2, changed=2` because it ran both the `git_retrieve` task (delegated via `run_once`) and its own EOS diff. All other devices show `ok=1, changed=1` -- just their vendor-specific diff task. The 1 skipped task per device is the diff task for the other platform (EOS devices skip the NX-OS diff and vice versa).

The `changed` status on the diff tasks is misleading -- no configuration was actually changed on any device. The modules report `changed` because a difference was detected between running and intended config, not because they modified anything. This is a known behavior of `diff_against: intended`.

== What To Do With the Drift

The operator has two options:

Bring devices back to intended state::
Run the `restore.yml` playbook to push the intended config from Git back to the devices, which would remove the SNMP community strings.

Update the intended config to match::
Run a backup playbook to export the current running configs and commit them to the Git branch, making the SNMP community part of the new intended state.

Which option is correct depends on whether the SNMP change was intentional and should be kept. This is the value of the backups-as-code pattern -- drift is detected automatically, and the decision about how to resolve it is left to the operator.

== Module summary

In this module, you learned how to:

* Capture a known-good fabric snapshot by running the backup workflow with a named branch (`final_configs`), preserving the fully configured EVPN VXLAN state as a Git-versioned restore point
* Use `diff_against: intended` with `cisco.nxos.config` and `arista.eos.eos_config` to compare each device's running configuration against a stored intended config without pushing any changes to the network
* Read the diff output to pinpoint exactly which lines differ between the running and intended configurations -- recognizing that `changed: true` in the play recap indicates a detected difference, not an applied modification
* Identify drift caused by the SNMP community string (`snmp-server community vxlan`) that was added during the tuning module but never committed to the `vxlan_configs` branch
* Choose between two remediation paths: restoring devices to a previous backup branch to remove the drift, or updating the intended config branch to accept the current state as the new baseline
* Restore device configurations to any named Git branch (`initial_config` or `final_configs`) using the self-service restore workflow, returning the fabric to a known-good state in minutes

The backups-as-code pattern built across this workshop -- automated backups, versioned Git branches, drift detection, and one-click restores -- provides a complete lifecycle for network configuration management that eliminates manual troubleshooting and makes configuration state auditable at every point in time.
