== Step 3: Examining the Inventory as Code

NOTE: **Level Set -- Why Inventories Matter** +
An Ansible inventory defines _what_ you automate against. Without an inventory, Ansible has no targets -- no playbook can run. Inventories organize hosts into groups with shared variables, enabling you to apply the right configuration to the right devices at scale. In network automation, where you manage dozens or hundreds of switches and routers across multiple vendors, a well-structured inventory is the foundation for consistent, repeatable automation.

The scope of a `play` within a `playbook` is limited to the groups of hosts declared within an Ansible **inventory**. Ansible supports multiple link:http://docs.ansible.com/ansible/latest/intro_inventory.html[inventory^] types. An inventory could be a simple flat file with a collection of hosts defined within it or it could be a dynamic script (potentially querying a CMDB backend) that generates a list of devices to run the playbook against.

In this lab you will work with an automation controller GUI based inventory called "Workshop Inventory". The "Workshop Inventory" was pre-configured during the lab setup using controller_as_code. 

NOTE: **Level Set -- What is Controller as Code?** +                                                                                                             
Controller as Code is the practice of defining your entire Ansible Automation Platform configuration -- inventories, credentials, job templates, workflows, team
s, and RBAC -- as Ansible playbooks rather than clicking through the GUI. It uses the `ansible.controller` collection, which provides modules like `ansible.cont
roller.inventory`, `ansible.controller.group`, `ansible.controller.host`, and `ansible.controller.job_template` to create and manage controller objects programm
atically. This approach makes your automation platform reproducible, version-controlled, and auditable: you can rebuild a controller from scratch, track every c
hange in Git, and promote configurations consistently across dev, staging, and production environments.        

The snippet below is from the playbook `controller_workshop_objects.yml` and shows how the Workshop Inventory was pre-provisioned for your pod using controller as code. Notice how the groups, hosts, and related groups are constructed using modules from the `ansible.controller` collection:

[source,yaml]

    name: "Workshop Inventory"
    organization: "Red Hat network organization"
    state: present
    controller_host: "{{ controller_endpoint.rstrip('/') }}"
    controller_username: "{{ controller_username }}"
    controller_password: "{{ controller_password }}"
    validate_certs: "{{ controller_verify_ssl | default(false) }}"

# Groups

- name: "Group — cisco_leafs"
  ansible.controller.group:
    name: cisco_leafs

      ansible_host: containerlab

NOTE: **Level Set -- What is NetBox?** +
NetBox is an open-source web application that serves as an Infrastructure Resource Modeling (IRM) tool and source of truth for network infrastructure. It's designed to document and manage IP address management (IPAM), data center infrastructure (racks, devices, cables), network equipment inventory, virtualization resources, and circuits and connections. +
 +
**Why use NetBox as an Ansible inventory source?** +
Instead of maintaining static YAML/INI files, Ansible queries NetBox in real-time. Inventory automatically reflects infrastructure changes without manual updates, eliminating drift between documentation and automation.

== Step 11: Sync the Netbox Inventory from the Automation Controller

. Navigate to | Inventories | Netbox Inventory | Sources | netbox_source | Sync
. Ensure that your inventory sync is a success. If it fails check the API Token that was pasted into the credentials.
. Review the source settings to understand the source configuration in AAP. Available options for an inventory source include:
+
--
* **Source** -- the inventory plugin type (e.g., NetBox, AWS, Azure, VMware, GCP, Red Hat Satellite, OpenStack, or a custom script)
* **Credential** -- the credential used to authenticate with the source
* **Source variables** -- YAML passed to the inventory plugin to control behavior (e.g., filtering, grouping, composing host variables)
* **Verbosity** -- the log level for the sync job (0=Normal through 5=WinRM Debug)
* **Update options**:
** _Overwrite_ -- replace all existing hosts/groups with the synced data (unchecked means merge)
** _Overwrite variables_ -- replace host/group variables rather than merging
** _Update on launch_ -- automatically sync the source each time a job template using this inventory runs
* **Cache timeout** -- how long (in seconds) to cache the inventory source results before re-querying
* **Execution Environment** -- the container image used to run the sync
--

---
plugin: netbox.netbox.nb_inventory
validate_certs: false
config_context: false
group_by:
  #- sites
  - device_types

compose:
  ansible_network_os: custom_fields.ansible_network_os
  ansible_port: custom_fields.ansible_port
  ansible_host: custom_fields.ansible_host
  ansible_connection: custom_fields.ansible_connection
  ansible_become: custom_fields.ansible_become
----
