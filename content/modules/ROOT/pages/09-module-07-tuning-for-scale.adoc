= 1-7: Tuning for Scale
:source-highlighter: rouge
:toc: macro
:toclevels: 1

This module demonstrates why tuning playbooks for Ansible Automation Platform is critical to automation performance and protection against automation errors. As network fabrics grow, the default execution behavior -- running tasks one host at a time with no error boundaries -- becomes a bottleneck at best and a risk at worst. A playbook that works fine against 6 devices in a lab can overwhelm a controller or cascade failures across hundreds of devices in production if forks, serial execution, and error handling are not configured deliberately. Tuning controls like `forks`, `serial`, `max_fail_percentage`, and `throttle` let you balance speed against safety: pushing configuration fast enough to meet change windows while ensuring that a failure on one device does not propagate unchecked across the entire inventory. This module walks through these settings and shows how small adjustments to playbook execution parameters produce measurable improvements in job runtime, resource consumption, and fault isolation.

== Learning objectives

This section covers:

* Building a survey-driven Job Template that lets operators choose `serial` batch sizes, `max_fail_percentage` thresholds, and whether to inject an error -- all at runtime
* Running a canary deployment using stepped `serial` batches (`1, 50%, 100%`) to test on a single device before expanding to the rest of the inventory
* Observing how `max_fail_percentage: 0` aborts the entire rollout when any host fails, protecting untouched devices from a bad configuration
* Comparing the blast radius of `max_fail_percentage: 0` vs. `50` -- seeing which healthy devices get configured and which are collateral damage
* Understanding how `forks` controls parallelism within each serial batch and when it becomes the bottleneck in larger inventories

NOTE: **Level Set -- Ansible Execution Controls for Scale and Safety** +
When Ansible runs a playbook, it processes each task across all targeted hosts before moving to the next task. Four key settings control how that execution is distributed, throttled, and protected from cascading failures: +
 +
**`forks`** +
The number of hosts Ansible manages in parallel during a single task. The default is 5, meaning Ansible opens SSH connections to 5 devices simultaneously, waits for all 5 to complete the current task, then moves to the next batch of 5. Increasing forks (e.g., to 25 or 50) speeds up execution across large inventories, but each fork consumes memory and CPU on the controller. Setting forks too high can exhaust controller resources, cause SSH timeouts, or overwhelm network devices that cannot handle many concurrent configuration sessions. In AAP, forks is set on the Job Template -- it overrides the system default for that specific job. +
 +
**`serial`** +
A play-level directive that splits the inventory into batches and runs the entire play (all tasks) against each batch before moving to the next. For example, `serial: 2` runs the full play on 2 hosts, then the next 2, then the next 2. This is different from `forks` -- forks controls parallelism _within_ a batch, while `serial` controls the batch size itself. `serial` is essential for rolling updates: you can push a configuration change to a small group of devices, verify it works, and then proceed to the next group. If a batch fails, the remaining batches are skipped, limiting the blast radius. You can also use percentages (`serial: "25%"`) or stepped lists (`serial: [1, 5, 10]`) to start cautiously and accelerate as confidence grows. +
 +
**`max_fail_percentage`** +
Works with `serial` to define how many hosts in a batch can fail before Ansible aborts the entire play. The default behavior (without `max_fail_percentage`) is to abort only when _all_ hosts in a batch fail. Setting `max_fail_percentage: 25` means that if more than 25% of hosts in a serial batch fail, Ansible stops immediately -- the remaining hosts in that batch and all subsequent batches are skipped. This prevents a bad configuration from rolling out across the entire inventory when early failures signal a systemic problem. For network automation, a low `max_fail_percentage` (e.g., 10-20%) is a critical safety net: if the first few devices reject a configuration change, you want to stop before the same broken change reaches every switch in the fabric. +
 +
**`throttle`** +
A task-level directive that limits how many hosts can execute that specific task concurrently, regardless of the `forks` setting. If `forks` is set to 50 but a particular task has `throttle: 5`, only 5 hosts will run that task at the same time. This is useful for tasks that interact with a shared resource -- for example, writing to a Git repository, calling a rate-limited API, or hitting a license server. Without `throttle`, all 50 forks would hit the shared resource simultaneously, causing contention or failures. `throttle` gives you fine-grained control at the task level without slowing down the entire playbook. +
 +
**How they work together** +
In practice, these controls are layered. `serial` sets the batch size for a rolling deployment. Within each batch, `forks` controls how many devices are configured in parallel. `max_fail_percentage` decides when to abort a batch early. And `throttle` can further restrict individual tasks that touch shared resources. A well-tuned playbook might use `serial: "25%"` with `max_fail_percentage: 10` at the play level, `forks: 25` on the Job Template, and `throttle: 1` on any task that commits to a Git repository -- giving you fast parallel execution with controlled rollout and safe abort boundaries.

== How `serial: [1, "50%", "100%"]` Produces Three Batches

Ansible processes the `serial` list left to right against the 6-host inventory (`leafs, spines`):

Batch 1 -- `1` (literal count)::
Takes 1 host: *leaf1*. This is the canary. If leaf1 fails, no other device is touched.

Batch 2 -- `"50%"` (percentage of total)::
50% of 6 = 3 hosts: *leaf2, leaf3, leaf4*. A small expansion after the canary succeeds.

Batch 3 -- `"100%"` (percentage of total)::
All remaining hosts: *spine1, spine2*. The final value in the `serial` list repeats for any leftover hosts, so `100%` means "take everyone that's left."

This is visible in the playbook output -- three separate `PLAY [Configure SNMP on Network Devices]` headers appear, each running the same task list against its batch:

[source]
----
PLAY [Configure SNMP on Network Devices]    ← batch 1: leaf1

PLAY [Configure SNMP on Network Devices]    ← batch 2: leaf2, leaf3, leaf4

PLAY [Configure SNMP on Network Devices]    ← batch 3: spine1, spine2
----

== How `max_fail_percentage: 0` Guards Each Batch

With `max_fail_percentage` set to `0`, Ansible aborts the entire play if *any* host in a batch fails. Combined with serial batching:

* If leaf1 (the canary) fails -> batches 2 and 3 never run. Only 1 of 6 devices is affected.
* If leaf3 fails during batch 2 -> batch 3 (the spines) never runs. At most 4 devices were attempted.
* Since `error` was `no`, the `fail` task was skipped on all hosts, so nothing failed and all three batches completed successfully.

== How `forks = 6` Fits In

The `forks` setting in `ansible.cfg` controls parallelism *within* a batch -- how many SSH connections Ansible opens simultaneously. With `forks = 6`:

[cols="1,1,1", options="header"]
|===
|Batch
|Hosts
|Forks Used

|1
|leaf1
|1

|2
|leaf2, leaf3, leaf4
|3 (parallel -- output is interleaved)

|3
|spine1, spine2
|2 (parallel)
|===

Since no batch exceeds 6 hosts, forks is never the bottleneck here. It would matter in a larger fabric -- if you had 20 leafs and `serial: ["50%"]`, a batch of 10 hosts would only run 6 at a time, with the remaining 4 queued until a fork frees up.

== How the Three Settings Work Together

[cols="1,1,1", options="header"]
|===
|Setting
|Value
|Role

|`forks`
|6
|Up to 6 hosts run tasks concurrently within a batch

|`serial`
|`[1, "50%", "100%"]`
|Splits hosts into batches: 1 canary, then 3, then the rest

|`max_fail_percentage`
|0
|If any host in a batch fails, abort remaining batches
|===

The combination is a controlled rollout: push to one device first (canary), if it succeeds push to a few more, if any failure occurs in any batch stop before touching the rest. This is a standard canary deployment pattern for network automation.

=== Batch 1: Canary Passes

[source]
----
PLAY [Configure SNMP on Network Devices]

TASK [Error] *******************************************************************
skipping: [leaf1]

leaf1 is an EOS device, so the `Error` task's `when:` condition (`ansible_network_os == 'cisco.nxos.nxos'`) evaluates to false and the task is skipped. The canary completes successfully -- SNMP is configured, and Ansible proceeds to batch 2.

=== Batch 2: Failure Triggers Abort

[source]
----
PLAY [Configure SNMP on Network Devices]

TASK [Error] *******************************************************************
skipping: [leaf2]
fatal: [leaf4]: FAILED! => {"changed": false, "msg": "This task just failed"}
fatal: [leaf3]: FAILED! => {"changed": false, "msg": "This task just failed"}

NO MORE HOSTS LEFT *************************************************************
----

Batch 2 contains leaf2 (EOS), leaf3 (NX-OS), and leaf4 (NX-OS). Since `forks = 6`, all three run the `Error` task in parallel:

* *leaf2* (EOS) -- skips the error task (wrong `ansible_network_os`)
* *leaf3* (NX-OS) -- `fatal: FAILED!` -- the `fail` module fires
* *leaf4* (NX-OS) -- `fatal: FAILED!` -- same

With `max_fail_percentage: 0`, *any* failure in the batch triggers an immediate abort. Two out of three hosts failed, which far exceeds the zero-tolerance threshold. Ansible prints `NO MORE HOSTS LEFT` and stops.

Critically, no remaining tasks execute for *any* host in this batch -- leaf2 skipped the error but never reaches the `Print` or `Configure SNMP` tasks. When `max_fail_percentage` aborts a batch, it kills the entire batch, not just the failed hosts.

=== Batch 3: Never Runs

spine1 and spine2 were scheduled for batch 3 (`"100%"` -- the remainder). Because batch 2 was aborted, batch 3 is never attempted. The spines are completely untouched -- they don't even appear in the output.

This is the protection that `serial` + `max_fail_percentage: 0` provides: the NX-OS failure in the leaf batch cannot propagate to the spine tier.

=== Batch Formation

With `serial: ["50%", "100%"]` against 6 hosts:

Batch 1 -- `"50%"`::

Remaining hosts: *leaf4, spine1, spine2*.

=== Batch 1: 1 of 3 Fails -- Under the 50% Threshold

[source]
----
PLAY [Configure SNMP on Network Devices]

TASK [Error] *******************************************************************
skipping: [leaf2]
skipping: [leaf1]
fatal: [leaf3]: FAILED! => {"changed": false, "msg": "This task just failed"}

TASK [Print the Name of the devices] *******************************************
ok: [leaf1] => { "msg": "leaf1" }
ok: [leaf2] => { "msg": "leaf2" }

TASK [Configure SNMP on Cisco NX-OS devices] ***********************************
skipping: [leaf1]
skipping: [leaf2]

TASK [Configure SNMP on Arista EOS devices] ************************************
ok: [leaf1]
changed: [leaf2]
----

Batch 1 contains leaf1 (EOS), leaf2 (EOS), and leaf3 (NX-OS). All three run the `Error` task in parallel:

* *leaf1* (EOS) -- skips the error task
* *leaf2* (EOS) -- skips the error task
* *leaf3* (NX-OS) -- `fatal: FAILED!`

One out of three hosts failed -- that is 33%, which is *under* the `max_fail_percentage: 50` threshold. Ansible removes leaf3 from the batch but *continues running the remaining tasks* for leaf1 and leaf2. Both EOS leafs proceed through `Print`, skip the NX-OS SNMP task, and get their EOS SNMP configuration applied.

NOTE: leaf1 shows `ok` (not `changed`) for the SNMP task because it was already configured in the earlier runs. leaf2 shows `changed` because this is the first time it successfully reached the SNMP task (in run 2, it was killed by the batch abort before the SNMP task could execute).

This is the key difference from run 2: with `max_fail_percentage: 0`, the same leaf3 failure would have aborted the entire batch and leaf2 would never have been configured. With `max_fail_percentage: 50`, the healthy hosts survive.

=== Batch 2: 1 of 3 Fails -- Under the 50% Threshold Again

[source]
----
PLAY [Configure SNMP on Network Devices]

TASK [Error] *******************************************************************
skipping: [spine1]
skipping: [spine2]
fatal: [leaf4]: FAILED! => {"changed": false, "msg": "This task just failed"}

TASK [Print the Name of the devices] *******************************************
ok: [spine2] => { "msg": "spine2" }
ok: [spine1] => { "msg": "spine1" }

TASK [Configure SNMP on Cisco NX-OS devices] ***********************************
skipping: [spine2]
skipping: [spine1]

TASK [Configure SNMP on Arista EOS devices] ************************************
changed: [spine2]
changed: [spine1]
----

Batch 2 contains leaf4 (NX-OS), spine1 (EOS), and spine2 (EOS):

* *spine1* (EOS) -- skips the error task
* *spine2* (EOS) -- skips the error task
* *leaf4* (NX-OS) -- `fatal: FAILED!`

Again, 1 of 3 hosts failed (33% < 50%), so Ansible drops leaf4 and continues. Both spines proceed through the remaining tasks and get SNMP configured.

Because batch 1 succeeded (under the threshold), batch 2 was allowed to run at all. And because batch 2 also stayed under the threshold, it completed to the end. The spines -- which were completely untouched in run 2 -- are now configured.

== Module summary

In this module, you learned how to:

* Create a survey-driven Job Template that exposes `serial`, `max_fail_percentage`, and error injection as operator-selectable parameters at launch time
* Execute a controlled canary rollout using `serial: [1, "50%", "100%"]` -- deploying to a single device first, then half the inventory, then the remainder -- and observe the three separate batch executions in the job output
* Verify that `max_fail_percentage: 0` provides zero-tolerance protection: a single NX-OS failure in batch 2 aborted the entire rollout and left the spines completely untouched
* Compare the impact of raising `max_fail_percentage` to `50`: the same two NX-OS devices failed, but healthy EOS devices in each batch continued to completion and the spines were configured -- reducing collateral damage from 3 skipped devices to 0
* Interpret the play recap to distinguish between devices that were configured (`changed`), devices that failed (`failed`), and devices that were protected by the batch abort (not listed in the recap at all)
* Recognize that `forks` controls parallelism within each serial batch -- in this lab `forks: 6` was never the bottleneck, but in a larger inventory it determines how many devices run tasks concurrently within each batch

These execution controls -- `serial`, `max_fail_percentage`, `forks`, and `throttle` -- are essential for scaling network automation safely. Without them, a single bad configuration change can propagate across an entire inventory before anyone notices the failure.
