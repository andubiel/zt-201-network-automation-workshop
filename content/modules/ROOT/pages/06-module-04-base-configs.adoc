NOTE: **Level Set -- What is EVPN VXLAN and Why Base Configs Come First** +
EVPN VXLAN is a modern data center fabric architecture that combines two technologies: **VXLAN** (Virtual Extensible LAN) creates Layer 2 overlay tunnels across a Layer 3 underlay network, allowing VLANs to stretch across the entire fabric without traditional spanning tree limitations. **EVPN** (Ethernet VPN) is the control plane that distributes MAC and IP address information between switches, replacing flood-and-learn with efficient, targeted forwarding. Together, they enable scalable multi-tenant networks over a spine-leaf topology. +
 +
Building an EVPN VXLAN fabric follows a deliberate bottom-up order. Before configuring the **underlay** (the routed Layer 3 network between spines and leafs) or the **overlay** (the VXLAN tunnels and EVPN peering), you need the foundational **base configuration** in place: VLANs that define your Layer 2 segments, loopback interfaces that serve as VTEP (VXLAN Tunnel Endpoint) addresses, and basic interface settings. Without these building blocks, the underlay has nothing to route and the overlay has nothing to encapsulate. +
 +
**Why automate this with Ansible?** +
Manually configuring base settings across a multi-vendor spine-leaf fabric is tedious and error-prone -- a mistyped VLAN ID on one leaf or an inconsistent loopback address can silently break VXLAN tunneling and take hours to troubleshoot. With Ansible resource modules, you define the intended base configuration once in structured YAML and push it consistently to every device, regardless of vendor. The modules are idempotent, so re-running the playbook corrects any drift without duplicating configuration. And because the same data model works across Arista EOS and Cisco NX-OS, you eliminate the need to maintain separate CLI scripts for each platform -- one playbook, one source of truth, applied uniformly across the entire fabric. This module focuses on automating that base layer using Ansible resource modules.

== Learning objectives

IMPORTANT: **The base configuration is the foundation that every subsequent layer depends on.** The underlay module builds OSPF and BGP peering on top of the loopback addresses and point-to-point links configured here. The overlay module then establishes VXLAN tunnels and EVPN peering using those same loopbacks as VTEP sources. A misconfigured VLAN, a missing loopback, or an incorrect /31 address at this stage will silently break underlay adjacencies and prevent overlay tunnels from forming -- and the failure may not surface until two modules later. Getting the base right, and proving it with automated tests, is not optional preparation; it is the critical first step of a working EVPN VXLAN fabric.

This section covers:

* Running a three-stage **Backup → Deploy → Test** workflow to safely provision base fabric configuration across a multi-vendor spine-leaf topology
* Interpreting resource module output -- reading the `changed`, `commands`, `before`, and `after` fields to verify what was applied to each device
* Understanding how the `base_fabric` role dispatches to vendor-specific task files and configures five resource layers: hostname, VLANs, interfaces, L2 switchports, and L3 addresses
* Using `state: merged` to layer intended configuration onto devices without disturbing existing settings
* Validating deployments with automated ping tests, interface checks, and hostname verification
* Diagnosing and recovering from a broken configuration using the backup-and-restore workflow

==== Role Dispatch Pattern

The base_fabric role uses a single-line main.yml to route to vendor-specific task files:

[source:yaml]
  ----
  - name: Route execution by Network Operating System
    ansible.builtin.include_tasks: "{{ ansible_network_os.split('.')[-1] }}.yml"
  ----

This splits arista.eos.eos into eos and cisco.nxos.nxos into nxos, dynamically including the correct task file. 
Both vendor files configure the same five resource categories using their respective collection modules: 
hostname, VLANs, interface state, L2 switchports, and L3 IP addresses. 
The Arista file additionally enables ip routing.

=== Workflow Overview

The base configuration module follows a three-stage workflow: **Backup → Deploy → Test**. Each stage is run as a separate job template from the Ansible Automation Controller.

. **Backup** -- Run the `1-2-Backups_as_Code-Backup-GIT` job template to snapshot every device's running configuration before making changes.
Name the branch something meaningful like `pre_base_config`.
+
This backup is your recovery point.
If the base configuration introduces an issue, use the `1-2-Backups_as_Code-Git-Restore` job template to select this branch and roll devices back to their exact pre-base state.

. **Deploy** -- Launch the `1-4-Base_Configs-Deploy` job template to push base fabric configuration to all spines and leafs:
+
* Hostnames
* VLANs
* Loopback interfaces
* Point-to-point links
* Switchport assignments
+
The playbook uses the `base_fabric` role, which dispatches to the correct vendor-specific task file based on each device's `ansible_network_os`.

. **Test** -- Launch the `1-4-Base_Configs-Test` job template to validate the deployment.
The test playbook checks:
+
* Management interfaces are up
* Ping tests from each leaf to both spine neighbors
* Hostnames match the inventory
+
If any test fails, review the output to identify the misconfigured device before proceeding to the underlay module.

TIP: In production always take a backup before and after major configuration changes. The backup branches in the GIT repository give you named restore points at every stage of the fabric build -- `pre_base_config`, `post_base_config`, `pre_underlay`, and so on. If something goes wrong in a later module, you can restore to the last known-good state without manually reconfiguring devices.

    "vlan 40",

  "before": [                                   // <3>

      "vlan_id": 1,
      "name": "default",

    }
  ],
  "after": [                                    // <4>
    { "vlan_id": 1, "name": "default", "state": "active" },
    { "vlan_id": 40, "name": "Data_VLAN_40", "state": "active" },
    { "vlan_id": 50, "name": "Data_VLAN_50", "state": "active" },
    { "vlan_id": 60, "name": "Data_VLAN_60", "state": "active" },
    { "vlan_id": 101, "name": "L3VNI_Transit", "state": "active" }
  ]
}
----
<1> **changed: true** -- the device was modified. The VLAN configuration did not match the intended state, so the module applied changes. On a subsequent run this would be `false` (idempotent -- no changes needed).
<2> **commands** -- the exact NX-OS CLI commands sent to the device. Four VLANs were created: `Data_VLAN_40`, `Data_VLAN_50`, `Data_VLAN_60` for host traffic, and `L3VNI_Transit` (VLAN 101) which will be used later by the VXLAN overlay as the Layer 3 VNI transit VLAN.
<3> **before** -- the VLAN configuration on the device _before_ the module ran. Only the default VLAN 1 existed -- the device had no data or transit VLANs configured.
<4> **after** -- the VLAN configuration _after_ the module ran. All four intended VLANs are now present and active alongside the default VLAN. This confirms the base VLAN layer is in place and ready for the underlay and overlay stages.

The `state: merged` parameter used in this task adds the defined VLANs without removing any existing configuration. This is the appropriate choice for base configuration where you want to layer new settings on top of whatever is already on the device.

Review the other task outputs to see how each resource module configures a different layer of the base fabric.

==== Base Tasks Overview

The `base_fabric` role runs five resource module tasks per device (with vendor-specific modules dispatched automatically). Each task handles one layer of the base configuration:

[cols="1,2,2,3",options="header"]
|===
| Order | Task | Cisco NX-OS Module | What It Configures

| 1
| Set Hostname
| `cisco.nxos.nxos_hostname`
| Configures the device hostname to match `inventory_hostname`, ensuring every switch is identifiable in logs, LLDP, and CLI prompts.

| 2
| Configure VLANs
| `cisco.nxos.nxos_vlans`
| Creates the data VLANs (40, 50, 60) for host-facing ports and the L3VNI transit VLAN (101) used later by the VXLAN overlay. Uses `state: merged` to add VLANs without disturbing existing ones.

| 3
| Enable Interfaces
| `cisco.nxos.nxos_interfaces`
| Brings up all spine-facing, host-facing, and loopback interfaces by setting `enabled: true`. Interfaces that are admin-down will not pass traffic, so this task ensures every link in the fabric is active.

| 4
| Configure L2 Switchports
| `cisco.nxos.nxos_l2_interfaces`
| Assigns host-facing ports to their respective access VLANs (e.g., Ethernet1/7 on leaf3 → VLAN 40). This determines which VLAN each connected host belongs to.

| 5
| Configure L3 IP Addresses
| `cisco.nxos.nxos_l3_interfaces`
| Assigns IP addresses to loopback interfaces (used as VTEP and router-ID sources) and point-to-point spine-leaf links (the /31 subnets). These addresses form the foundation of the underlay routing configured in the next module.
|===

Below is the Cisco NX-OS task file (`nxos.yml`) from the `base_fabric` role:

[source,yaml]
----
- name: Configure Hostname [Cisco NX-OS]
  cisco.nxos.nxos_hostname:
    config:
      hostname: "{{ base_hostname }}"
    state: merged

- name: Configure VLANs [Cisco NX-OS]
  cisco.nxos.nxos_vlans:
    config: "{{ base_vlans | default([]) }}"
    state: merged
  when: base_vlans is defined

- name: Configure Interfaces Description and State [Cisco NX-OS]
  cisco.nxos.nxos_interfaces:
    config: "{{ base_interfaces }}"
    state: merged

- name: Configure L2 Switchports [Cisco NX-OS]
  cisco.nxos.nxos_l2_interfaces:
    config: "{{ base_l2_interfaces | default([]) }}"
    state: merged
  when: base_l2_interfaces is defined

- name: Configure L3 IP Properties [Cisco NX-OS]
  cisco.nxos.nxos_l3_interfaces:
    config: "{{ base_l3_interfaces }}"
    state: merged
----

Each task pulls its configuration from `host_vars` or `group_vars` variables (`base_hostname`, `base_vlans`, `base_interfaces`, etc.), keeping the task file generic and reusable. The `when: base_vlans is defined` and `when: base_l2_interfaces is defined` conditionals allow spines to skip VLAN and switchport tasks since they only need L3 configuration. The Arista EOS task file (`eos.yml`) follows the same five-task pattern using `arista.eos.*` modules and additionally enables `ip routing` on the device. Both vendor files use `state: merged`, which is additive -- it applies the intended settings without removing any existing configuration.

== Module summary

In this module, you learned how to:

* Execute the three-stage base configuration workflow -- **Backup → Deploy → Test** -- from the Ansible Automation Controller, and understand why taking a named backup branch before every configuration change gives you a reliable rollback point
* Review device backup files in Gitea to verify that running configurations were captured before any base changes were applied
* Read the structured output of a resource module (`cisco.nxos.nxos_vlans`) and interpret the `changed`, `commands`, `before`, and `after` fields to understand exactly what was configured and why
* Walk through the five-task `base_fabric` role -- hostname, VLANs, interface state, L2 switchports, and L3 IP addresses -- and see how the role dispatches to vendor-specific task files (`eos.yml` / `nxos.yml`) based on `ansible_network_os`
* Understand how `state: merged` adds intended configuration without removing existing settings, making it the right choice for layering base config onto devices
* Validate the deployment by reviewing the test playbook output -- management interface checks, neighbor ping tests, and hostname verification -- across all four leafs
* Deploy an intentionally broken configuration to spine1, observe the resulting test failures, and restore correct addressing using the backup-and-restore workflow

With the base layer verified, the fabric now has the VLANs, loopback addresses, and point-to-point links that the next two modules depend on. The underlay module will build OSPF and BGP peering over these links, and the overlay module will establish VXLAN tunnels and EVPN sessions using the loopbacks configured here as VTEP sources. Every layer above inherits the correctness of this one -- which is why the test step is not optional.
