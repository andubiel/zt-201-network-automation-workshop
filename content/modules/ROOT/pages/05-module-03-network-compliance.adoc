= 1-3: Network Compliance
:source-highlighter: rouge
:toc: macro
:toclevels: 1

NOTE: **Level Set -- Why Automated Network Compliance Matters** +
Manual compliance audits are slow, error-prone, and impossible to scale. A network engineer checking configurations by hand across dozens of devices can miss subtle drift -- a changed ACL, a missing NTP server, a mismatched SNMP community -- that silently degrades security or causes outages. Automated compliance with Ansible lets you define the intended state once and continuously validate every device against it. Deviations are detected instantly, reported clearly, and can be remediated in the same workflow. This shifts compliance from a periodic, reactive audit to a continuous, proactive process -- reducing risk, accelerating change windows, and providing auditable evidence that your network matches its documented standard.

Network resource modules make compliance checks straightforward -- by using the `state: replaced` parameter, you can define the intended configuration and let Ansible enforce it across your devices. Running the playbook in **check mode** lets you preview what would change without touching the device, giving you a safe way to audit compliance. When you're ready to remediate, switching to **run mode** applies the changes to the remote devices. For production environments, **Approval Nodes** in an AAP workflow add a human gate between the check and the apply -- pausing execution so an operator can review the proposed changes or troubleshoot before anything is pushed to live infrastructure.

A workflow in Ansible Automation Platform chains multiple job templates into a single, orchestrated process with built-in decision logic. Each node in a workflow can follow a **success**, **failure**, or **always** path, letting you build branching logic without writing any code -- for example, run a compliance check, and only proceed to remediation if drift is detected. Workflows also support **Approval Nodes**, which pause execution and require a human to approve before continuing -- critical for production changes where you want a review gate between detection and remediation. This turns a collection of individual playbooks into a repeatable, auditable pipeline that operators can launch with a single click from the AAP UI, complete with role-based access control and centralized logging.

NOTE: **Level Set -- Understanding the logging_global Resource Module Output** +
`logging_global` is a network resource module -- a category of Ansible modules designed to manage one specific section of a device's configuration declaratively. Instead of sending raw CLI commands, you define the desired logging configuration in structured YAML, and the module handles the translation to vendor-specific commands. +
+
The module output includes three key fields that make compliance visible: +
+
* **`state`** -- tells the module what action to take. With `replaced`, the module enforces exactly what you defined: it adds missing configuration, removes anything extra, and leaves unrelated config sections untouched. In check mode, it calculates what _would_ change without applying it. +
* **`before`** -- the logging configuration currently running on the device, captured before any changes. This is your baseline. +
* **`after`** -- the intended logging configuration that would be applied. Comparing `before` and `after` shows you exactly what is out of compliance -- which syslog servers are missing, which logging levels differ, and what would be added or removed to bring the device into the desired state. +
+
This before/after comparison is what the operator reviews at the approval node before deciding whether to proceed with remediation.
+
. Review the Data output
+

    }
  }

----
<1> **commands** -- the exact CLI commands the module _would_ send to the device. In check mode these are calculated but not applied. This is the most actionable field for an operator reviewing the approval node -- it shows precisely what will change.
<2> **before** -- the logging configuration on the device _before_ any changes. An empty `{}` means the device had no logging configuration in this resource scope.
<3> **after** -- the logging configuration that _would_ exist after applying the changes. Comparing `before` and `after` reveals every deviation from the intended state. However, in check mode the `after` is always the same as the `before`. 
<4> **changed** -- `true` indicates the device is out of compliance and changes are needed. If the device already matches the intended state, this would be `false` and `commands` would be empty.
<5> **config** -- the intended logging state you defined in your playbook. This is the "source of truth" that the module compares against the device. It includes the logfile destination, console and monitor severity levels, syslog server hosts, and facility overrides.
<6> **state: replaced** -- tells the module to enforce _exactly_ this configuration: add anything missing, remove anything extra, and leave unrelated config sections untouched.

NOTE: **Level Set -- Enabling Check Mode** +
Check mode can be enabled at multiple levels. In the **Ansible Automation Controller**, you enable it on a job template by toggling the `Enable check` option under the job template settings -- this adds a checkbox when launching the job, letting operators choose check mode at runtime. In a **workflow**, this means you can have two nodes pointing at the same job template: one configured with check mode for the compliance audit, and one without for the actual remediation. +
 +
At the **playbook level**, you can also set `check_mode: true` on an individual task or on an entire play. This is useful when you want _some_ tasks to always run in check mode regardless of how the job is launched -- for example, an audit task that should never make changes. When check mode is enabled at the job template level in AAP, it overrides the playbook setting and forces _all_ tasks into check mode for that run.

=== Understanding the Diff Output

When `diff_mode: true` is enabled on the job template, Ansible produces a unified diff comparing the `before` and `after` states. Below is the diff output from the compliance check on `leaf3`:

[source,diff]
----
--- before
+++ after
@@ -1 +1,29 @@
-{}
+{
+    "console": {
+        "severity": "critical"
+    },
+    "facilities": [
+        {
+            "facility": "local5",
+            "severity": "notification"
+        }
+    ],
+    "hosts": [
+        {
+            "host": "1.1.1.2",
+            "severity": "informational"
+        },
+        {
+            "host": "1.1.1.3",
+            "severity": "informational"
+        }
+    ],
+    "logfile": {
+        "name": "messages",
+        "severity": "notification",
+        "size": 12000
+    },
+    "monitor": {
+        "severity": "warning"
+    }
+}
----

Reading the diff:

* **`--- before`** -- the logging configuration currently on the device. In this case `{}` (empty) means the device has no logging configuration in this resource scope.
* **`+++ after`** -- the intended logging configuration that _would_ be applied. Every line prefixed with `+` is something that will be added to bring the device into compliance.
* **`@@ -1 +1,29 @@`** -- the diff header showing the scope of the change: 1 line removed (the empty `{}`), 29 lines added (the full intended configuration).
* **`changed: true`** -- confirms the device is out of compliance and changes are pending approval.

In this example, `leaf3` had _no_ logging configuration at all. The diff shows every piece of the intended state being added: console logging at critical severity, a local5 facility, two syslog servers (`1.1.1.2` and `1.1.1.3`), a logfile destination, and monitor logging at warning level. This is exactly what the operator reviews at the approval node -- a clear, readable summary of everything that will change before clicking approve.


== Step 5: Understand the Compliance Playbook Tasks from `1-3-network_compliance/roles/logging/tasks/cisco.nxos.nxos.yml` on VSCode.

=== Task 1: Check/Apply NXOS Logging Configuration

[source,yaml]
----
- name: Check/Apply NXOS logging configuration
  cisco.nxos.nxos_logging_global:
    config: "{{ logging_nxos }}"
    state: replaced
  notify: Logging compliance violation
  register: logging_diff
----

`cisco.nxos.nxos_logging_global` is a resource module that manages the entire logging configuration on a Cisco NX-OS device declaratively.

* **`config: "{{ logging_nxos }}"`** -- the desired logging state, defined as a structured data model (in `group_vars` or `host_vars`). This is not raw CLI commands -- it is a YAML dictionary describing syslog servers, log levels, and facilities.
* **`state: replaced`** -- replaces the device's current logging config with exactly what is defined in `logging_nxos`. Anything on the device that is not in the variable gets removed; anything missing gets added. This enforces the config as the single source of truth.
* **`notify: Logging compliance violation`** -- triggers a handler only if the module made changes (i.e., the device was out of compliance). If the config already matched, no handler fires. This is how the playbook flags drift.
* **`register: logging_diff`** -- captures the module's return data, which includes `before` (the device's config before the task ran) and `after` (the config after). This is consumed by the next task.

=== Task 2: Compare Before and After

[source,yaml]
----
- name: Compare before and after logging configurations
  ansible.utils.fact_diff:
    before: "{{ logging_diff.before }}"
    after: "{{ logging_nxos }}"
  delegate_to: localhost
----

`ansible.utils.fact_diff` produces a human-readable diff between two structured data objects -- similar to a `diff` on two files, but operating on Ansible facts and variables.

* **`before: "{{ logging_diff.before }}"`** -- the device's actual logging config captured from the previous task's registered output.
* **`after: "{{ logging_nxos }}"`** -- the desired state (`logging_nxos`), displayed earlier in `group_vars/cisco.yml` -- this compares what the device _had_ against what the policy says it _should_ have.
* **`delegate_to: localhost`** -- the comparison is pure data manipulation, so it runs locally rather than on the network device.

The output shows exactly which logging settings were added, removed, or changed -- giving operators a clear view of what was out of compliance and what the playbook corrected.

=== Understanding the Run Mode Output

After the approval node is approved, the compliance workflow re-runs the playbook in **run mode**, applying the changes to the devices. Below is the output from `leaf3` after remediation:

TASK [roles/logging : Check/Apply NXOS logging configuration]

[source,json]
----
{
  "commands": [                                   // <1>
    "logging console 2",
    "logging monitor 4",
    "logging logfile messages 5 size 12000",
    "logging level local5 5",
    "logging server 1.1.1.2 6",
    "logging server 1.1.1.3 6"
  ],
  "before": {},                                   // <2>
  "after": {                                      // <3>
    "logfile": {
      "name": "messages",
      "severity": "notification",
      "size": 12000
    },
    "hosts": [
      { "host": "1.1.1.2", "severity": "informational" },
      { "host": "1.1.1.3", "severity": "informational" }
    ],
    "monitor": { "severity": "warning" },
    "facilities": [
      { "facility": "local5", "severity": "notification" }
    ]
  },
  "changed": true                                 // <4>
}
----
<1> **commands** -- the CLI commands that were _actually sent_ to the device this time. In check mode these were only calculated; in run mode they were executed.
<2> **before** -- the device's logging configuration before remediation. The empty `{}` confirms there was no logging config on `leaf3` prior to this run.
<3> **after** -- the device's logging configuration _after_ remediation. Unlike check mode (where `after` mirrors `before`), run mode shows the real post-change state. This confirms the device now has the intended logfile, syslog servers, monitor level, and facility configuration.
<4> **changed: true** -- confirms the module made changes. The device was out of compliance and has now been remediated.

The key difference from the check mode output is the `after` field: in check mode it was empty (no changes were applied), but in run mode it reflects the actual configuration now running on the device. This is confirmation that the remediation succeeded -- `leaf3` now matches the intended logging state defined in `group_vars/cisco.yml`.
